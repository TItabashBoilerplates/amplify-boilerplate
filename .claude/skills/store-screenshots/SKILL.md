# ストア掲載画像スキル

App Store / Google Play の掲載画像を、**アプリの実画面から**作って反映する手法。
React Native / Expo アプリ全般に適用できる。

このスキルは**方法**を持つ。個々のプロジェクトの具体的な配線（画面の一覧、コピー、
スロット割り当て）は、そのリポジトリの設計ドキュメントに置くこと。
末尾の「本リポジトリでの実体」に、用意済みのコマンドと配置をまとめてある。

## 全体の流れ

```
1. 素材を撮る    モックデータで実アプリを描画 → 端末の実解像度で書き出し
2. 背景を作る    画像生成モデルで「背景 + 見出しの文字」
3. 合成する      背景の上にアプリ画面とロゴを**ピクセル等倍**で重ねる
4. 反映する      ストアの API で push（必ず dry-run で差分を見てから）
```

**端末クラス（スマホ / タブレット）ごとに 1〜3 をやり直す。**
比も枚数も構成も別物で、流用できない（4 節）。

## 1. 素材の撮影 — モックデータで実機に描かせる

### 撮影経路は 2 つある。画面ごとに選ぶ

| 経路 | 何を撮るか |
|---|---|
| **シミュレータ / エミュレータ**（本リポジトリ: `screenshots-mobile`） | アプリと同じ Metro / スタイルパイプラインで描画され、実解像度そのままで書き出せる。**ネイティブ部品・shadow/elevation・セーフエリアが写る画面はこちら必須** |
| **Storybook**（本リポジトリ: `screenshots-storybook`） | react-native-web の描画。**到達しづらい状態**（空・エラー・特定データ）や**多ロケール × 多サイズの量産**に強い。ネイティブビルド不要 |

Storybook 経路の弱点は**実機と見た目が食い違うこと**なので、そこだけを機械的に検出する:
`native-control`（input/select/switch は RN では OS 部品になり別物）・`shadow`（CSS
`box-shadow` と iOS `shadow*` / Android `elevation` は描画が一致しない）・
`broken-image`。検出されたら実機描画で撮り直す。

> **Expo Web で撮ろうとしない。** `react-native` の一部モジュールに web 解決子が無く
> バンドルが落ちる。直しても地図・カメラ・課金・広告 SDK が順に web 非対応で刺さる。

### 撮影用のルートを本体と分ける

expo-router なら、環境変数が立っているときだけ **router root を撮影用ディレクトリへ
差し替える**。`require.context` はそのディレクトリ 1 つにしか張られないので、
**通常のビルドには撮影用の画面もフィクスチャも画像も入らない**。

```ts
// app.config.ts — 差し替えるのは plugin の引数
const withShotsRouterRoot = (plugin) =>
  Array.isArray(plugin) && plugin[0] === 'expo-router' && process.env.SHOTS === '1'
    ? ['expo-router', { ...plugin[1], root: './shots/screens' }]
    : plugin
```

> **`extra.router.root` を書き換えても効かない。** expo-router の config plugin は
> 動的設定より後に走って `extra.router` を上書きするため、**エラーにならず静かに無視される**。

### データはクエリキャッシュを先に埋めて供給する

画面が TanStack Query 越しにしかデータを見ないなら、**キャッシュを先に埋めれば
`queryFn` は一度も走らない**。API クライアントを差し替える必要も、サーバを模す必要もない。

```ts
new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: Number.POSITIVE_INFINITY,
      gcTime: Number.POSITIVE_INFINITY,
      retry: false,            // ネットワークが無いので、無いと数秒おきに再試行してちらつく
      refetchOnMount: false,
    },
  },
})
```

**キーは必ずアプリ側のキーファクトリから作る。** 手書きすると 1 文字違いでキャッシュに
当たらず、スケルトンのまま撮れてしまう。認証など Zustand で持っている状態は
`setState` で直接埋める。

### フィクスチャはアプリの規約に従う

日付の保存形式のような**アプリ側の約束**を破ると、画面に嘘の表示が出る。
「暦日を UTC 0 時で保存する」規約のフィールドに「今この瞬間」を入れると、
タイムゾーンによっては 1 日ずれて「期限切れ」と表示される。
**推測で埋めず、その値を読む関数の実装を確認する**（`.claude/rules/datetime.md`）。

### 見た目に影響する配線はハーネスにも写す

撮影用ルートはアプリ本体の `_layout` を通らない。**見た目を決めるものは明示的に写す**。

| 写すもの | 忘れるとどうなるか |
|---|---|
| フォント読み込み | 本文がシステムフォントで撮れる |
| ナビゲーションのテーマ | 地色が変わる |
| 画面コンテナのレイアウト制約 | タブレットだけ全幅で撮れる |

逆に、**外部と通信するもの（プッシュ通知 / 課金 / 広告 / 解析 / 位置情報）は外す**。

### 撮影ハーネスからは**全ルートを開けるようにする**

掲載に使う画面だけをハーネスに置くと、**それ以外の画面は崩れていても気づけない**。
崩れの巡回にも同じハーネスを使うので、アプリの全ルートに対応する入口を用意する。

| 罠 | 症状 | 対処 |
|---|---|---|
| ルートが無い | 主要な導線を押すと `Unmatched Route` になり、その先を確認できない | 本体のルート一覧と突き合わせて**差分をゼロにする** |
| データが無い | 詳細画面が「見つかりません」になり、**崩れを見られない** | 一覧のキャッシュだけでなく**詳細のキーも埋める** |
| 条件付きで出ない | 「未登録の人にしか出ない」画面が既定のフィクスチャでは開けない | **その画面だけ別のキャッシュを被せる**（既定を書き換えると後続の撮影が影響を受ける） |

### 掲載用の出力先と、巡回用の出力先を分ける

同じディレクトリへ書くと、**待ち時間の足りない撮り直しが掲載元を静かに上書きする**。
巡回のつもりで回した 1 回が、地図の描画前や遷移前の画面を掲載元に置き換える。

### タップは**座標で押さない**

セグメント切り替えやタイル選択のように、開いてから 1 タップ要る画面がある。
UI 自動化ツールに座標でタップさせると、**外れていても成功が返る**。
気づかないまま「選択されていない画面」を掲載してしまう。

- 押す対象に **`accessibilityLabel` を付けて文字で押す**（読み上げの品質も上がる）
- 固定の `sleep` ではなく、**要素が出るまで待つ**コマンドを使う
- 押した結果が反映されているかは、**撮った画像で確認する**

### ステータスバーを固定する

時刻・電波・電池が写り込むと、撮り直すたびに掲載画像が変わる。シミュレータの
ステータスバーは固定できる（Apple が販促素材で使う 9:41 が無難）。
**ハーネスが最後に解除する作りなら、手動で撮り足すときは自分で固定し直すこと。**

### 実行時にトークンが要る機能

地図など、実行時に API トークンが必要な画面がある。**そのキーだけを注入する**こと。
シークレットマネージャの本番 config をまるごと流すと、ローカルが本番バックエンドを向く。

```bash
SHOTS=1 MAP_TOKEN="$(aws ssm get-parameter --with-decryption \
  --name /amplify-boilerplate/mobile/MAP_TOKEN --query Parameter.Value --output text)" \
  npx expo start
```

値をコマンド置換で渡せば、ログにもファイルにも残らない（`.claude/rules/env-naming.md`）。

## 2. 背景と見出しの生成

日本語を含む見出しは、現行の画像生成モデル（`openai/gpt-image-2` 等）で**正しく組める**。
背景ごと生成させてよい。モデル選定と CLI の使い方は `.claude/skills/fal/`。

### 生成モデルに描かせてはいけないもの

| 要素 | 担当 | 理由 |
|---|---|---|
| 背景・装飾・**見出しの文字** | 画像生成モデル | 人手では出せない密度が短時間で出る |
| **アプリ画面** | 実スクショを等倍合成 | 描き直させると**存在しない UI を掲載**したことになる（2.3.3） |
| **アプリロゴ** | 実ファイルを等倍合成 | 実ファイルのほうが正確 |
| **数値・価格・実装に紐づく文言** | 合成するか、そもそも書かない | 実装と食い違うと 2.3.1 の指摘対象 |

### 生成モデルのサイズ制約を先に確認する

出力サイズには必ず上限がある（辺の倍数・最大辺・アスペクト比・総画素）。
**帯を 1 枚で生成できる幅がここで決まる**ので、構成を考える前に調べる。

例（gpt-image-2）: 両辺 16 の倍数・最大辺 3840px・アスペクト比 3:1 まで・
総画素 655,360〜8,294,400 → **スロット 2 枚ぶんが上限**。

### CLI 経由で叩くときの癖

| 事象 | 対処 |
|---|---|
| ネストしたオブジェクトが文字列として送られ 422 | `size[width]=2640` のようなブラケット記法 |
| 配列パラメータが「list であるべき」 | `image_urls[0]=<url>` |
| data URI を渡すとパーサが壊れる | ストレージへ上げて URL を得るか、API キーで REST を直接叩く |

## 3. 合成

### パノラマ（連結）を作るなら背景を上下 2 層に分ける

生成モデルは帯を 1 枚で作れない（上記の制約）。そこで:

| 層 | 誰が作るか | 継ぎ目 |
|---|---|---|
| 見出し帯（上） | 生成モデル（2 スロット単位） | その 2 枚の中でのみ連続 |
| 下地（下） | **単色の地色を自前で敷く** | 全スロットで完全に同一 |

下地が同一なので、**端末はどの継ぎ目でもまたげる**（端末は生成物ではなく合成物）。
生成単位の制約を、下地を自前にすることで回避できる。

### 繋げるのは 1・2 枚目だけ

iOS の検索結果に出るのは **1・2 枚目だけ**。繋げて大きく見せる価値があるのはそこに限られ、
3 枚目以降は 1 枚で意味が通らないと一覧で「割れた画像」に見える。

### 合成は HTML + ヘッドレスブラウザが速い

実フォントで日本語を組め、角丸・影・端末フレームも CSS で書ける。
**スロットごとに 1 枚描く**（背景を CSS でずらす）のが安全。画像切り出しツールの
オフセット原点は資料と実挙動が食い違うことがあり、**継ぎ目で見出しが文字の途中から割れる**。

### 端末フレームは自分で描く

実機のモックアップ画像は数年で古びるうえ、メーカーがプロダクトイメージの使用に
条件を課している。**ベゼルと角丸だけの中立な枠**を CSS で描けば両方を避けられる。

### 折り返しを禁止する

合成するテキストは 1 行ずつ `white-space: nowrap` にする。
折り返させると語の途中で割れ、一目で安っぽく見える。

### 見出しの下端より下から下地を始める

見出し帯と下地の境目をグラデーションで隠すとき、**フェードの開始位置
（`bandEnd - bandFade`）が見出しの下端より上にあると、2 行目が白く飛ぶ**。
見出しが 1 行のスロットでは気づかず、2 行のスロットだけ薄くなる。
端末を置く位置も見出しの下端より下にする（上に食い込むと角が文字に重なる）。

### 書き出す前に出力ディレクトリの画像を消す

スロット名を変えると**旧名のファイルが残り、新旧が混在したままストアへ上がる**。
`01-cover.png` と `01-home.png` が並ぶ、という形で出る。

### 端末の下端を切って、画面下部の常設 UI を落とす

開発ビルドの広告バナー（テスト広告）やデバッグ表示は、**そのまま撮ると掲載画像に載る**。

| 方法 | 向き | 注意 |
|---|---|---|
| 枠ごとキャンバスの外へ逃がす | 縦長のスロット（スマホ） | 四隅が無くなるので、横長の端末では「切れた板」に見える |
| 画面の下端を**切り落とす**（`overflow: hidden`） | 四隅を見せたいとき（タブレット） | 切る割合ぶん中身が減る |

## 4. 端末クラスを増やす（タブレット）

タブレットは**別のデバイスクラス**で、スマホの画像は流用されない。
`ios.supportsTablet: true` を宣言している限り、**タブレット用の画像が無いと提出できない**。

### スマホの構成をそのまま持ち込むと壊れる

| スマホでの作り | タブレットで起きること |
|---|---|
| 端末の下端をキャンバス外へ逃がす | **四隅の無い「切れた板」**になり、タブレットに見えない |
| 継ぎ目をまたがせて 2 スロットに 1 台 | **縦に割れた事故**にしか見えない |
| 端末を 1 台だけ置く | 横幅を使えず、左右が間延びする |

**タブレットは「1 スロット 1 台・四隅のある完全な枠・正面・中央」**にする。
広告バナー等は画面外へ逃がすのではなく、**下端を切り落として**消す。

### 向きは縦にする

> "**Depending on the orientation of your screenshots**, the first one to three images
>  will appear in search results when no app preview is available"

**検索結果に出る枚数が向きで変わる。** 横向きは 1 枚で幅を使い切るため実質 1 枚しか出ない。
縦向きなら最大 3 枚出るので、スマホと同じ「最初の数枚が勝負」という設計が使える。

### 引き伸ばして作らない・枚数は絞る

比が違う（1:2.17 と 1:1.33）ので、スマホ用を引き伸ばすと破綻する。
**タブレットで撮り直して、タブレット用に組み直す。** 枚数は **5〜8 枚**が定石。

### 画面の選び方が効く

縮小すると**フォームや設定画面は灰色の線の集合**にしかならない。掲載画像は
「見出しで意味を伝え、端末で"ちゃんとしたタブレットアプリ"だと示す」ものなので、
**写真が大きく写る画面か、独特のレイアウトを持つ画面**を選ぶ。

| 見出し | ❌ 選びがちな画面 | ✅ 差し替え先 |
|---|---|---|
| 「みんなで共有」 | 設定（項目が 2 件で下が空く） | メンバーが顔付きで並ぶ画面 |
| 「◯◯が片づく」 | 入力フォーム | 片づいた結果の一覧 |

**タブレットでしか作れない絵を主役に置く。** 一覧と詳細が同時に見える 2 ペインのように、
スマホでは撮れない画面が、タブレット版を別途出す理由そのものになる。
そこが 1 カラムのままなら、タブレット対応自体を見送るほうがよい。

### 合成の設定は端末クラスごとの表にする

スクリプトを 2 本に分けると、片方だけ直した状態が残る。
**1 ファイルの中に端末クラスごとの設定表**を持ち、切り替えて実行する。

## 5. ストアの制約（実装前に一次情報で確認する）

数字は変わる。**必ず公式ドキュメントで確認してから**作る。

| 項目 | App Store | Google Play |
|---|---|---|
| 枚数 | 1〜10 枚 | 最大 8 枚（公開には 2 枚以上） |
| スマホ | 最大クラスのサイズだけ出せば下位機種へ自動縮小 | **長辺 ≤ 短辺 × 2** という比率制約がある |
| タブレット | タブレット対応を宣言していれば**必須** | — |
| その他必須画像 | — | **フィーチャーグラフィック 1024x500** とアイコン 512x512 |
| 形式 | JPEG / PNG。**アルファ不可** | 同左 |

> **同じ画像を両ストアに使えないことがある。** 縦長のスマホ実解像度（1320x2868 = 2.17 倍）は
> Play の比率制約を超える。左右に地色を足して比率を収める。
> Android の既定エミュレータプロファイル（Pixel 7 = 1080x2400 = 2.22 倍）も**違反する**ので、
> 1080x1920 (16:9) の AVD を使う。

### 審査で効くガイドライン

| 条項 | 内容 | 影響 |
|---|---|---|
| **2.3.3** | "Screenshots should show the app in use, and not merely the title art... They may also include **text and image overlays**." | 見出しの焼き込みは**明示的に OK**。アプリ UI が 1 つも写らない面は NG |
| **2.3.7** | "Metadata such as app names, subtitles, **screenshots**, and previews should not include **prices**..." | **「無料」「◯円」をスクショに書けない**。料金は**説明文**に書く |

出典: [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)

## 6. ストアへの反映

**必ず dry-run で差分を見てから実行する。** どちらも本番の掲載情報を書き換える。

### App Store

**EAS Metadata はスクリーンショットを扱えない**（公式の対応表で "Upload screenshots ✗"）。
文言・カテゴリ・年齢レーティングまでで、画像は App Store Connect API を直接叩く。

API の流れは「予約 → 分割 PUT → checksum 付き commit → 並び順の PATCH」の 4 段。

| 注意 | 内容 |
|---|---|
| 表示タイプ | 新しい画面サイズの `screenshotDisplayType` は**公式リファレンスに載っていない**。値を誤ると API が 400 で許容値を返すので、**返ってきた値だけ**を登録する。推測で足さない |
| **端末クラスが複数あるとき** | セットは**端末クラスごとに分かれる**。「既存が 1 つならそれを使う」で拾うと、**タブレットの画像をスマホのセットへ入れる**。**型が一致するセットだけ**を対象にし、無ければ作る |
| 並び順 | アップロード順が保たれる保証は無い。**最後に PATCH で確定**する |
| アプリの特定 | **bundle id から引く**。設定ファイルのアプリ ID（`ascAppId`）は任意項目で、消えていることがある |
| バージョン | 編集できるのは `PREPARE_FOR_SUBMISSION` 等**準備中の版だけ**。審査中・公開済みは編集できない |
| JWT | ES256 の署名は `dsaEncoding: "ieee-p1363"` が必須。既定の DER だと 401 になり「鍵が違う」と誤診しやすい |

### Google Play

編集は **edit というトランザクション**単位。文言と画像で edit を分けると
片方だけ通った中途半端な掲載になりうるので、**まとめて 1 つの edit で commit** する。

- スクリーンショットは**複数枚 + 順番**。差分があれば**全消ししてから順に上げ直す**
  （1 枚ずつ足すと既存と並びが混ざる）
- **言語ごとに別物**。ある言語の画像を別言語の掲載に上げない
- 文言も同時に更新されるので、**スクショだけのつもりで実行しない**
- **購入シートのアイコンはストア掲載情報の `icon` を見る**（APK のランチャーアイコンではない）。
  未登録だと購入直前にプレースホルダが出る

### 資格情報

ストア API の鍵は、**リポジトリ横断で共有される場所**に置かれていることが多い。
プロジェクト名の config だけ見て「無い」と判断しない（本リポジトリでは
`config.env` の `MOBILE_TOKENS_PROJECT` / `MOBILE_TOKENS_CONFIG` がその配線）。

## 7. 落とし穴（どのプロジェクトでも起きる）

| 症状 | 真因 | 対処 |
|---|---|---|
| **全スロットが同じ絵になる** | dev クライアントの初回バンドル中に deep link を送ると読み込みが中断し、以降ずっとエラー画面を撮る | 初回バンドルより長く待つ。**連続するスクショのハッシュ重複を検査する** |
| **一部が真っ白のまま撮れる** | 地図・画像など描画が遅い要素を待たずに撮っている | 画面ごとに待ち時間を変える。**ファイルサイズの下限を検査する**（一様な面は PNG が極端に縮む） |
| **一部だけ撮り直すと別の画面を上書き** | ファイル名に通し番号を振っていた | 番号をやめて**画面名だけ**にする。掲載順は設計ドキュメントが持つ |
| 型チェックが無関係な場所で落ちる | 撮影用ルートで起動すると、型付きルートの生成物がそのルートで再生成される | 生成物を消す。**gitignore 済みなら CI には影響しない** |
| 日付が 1 日ずれる | フィクスチャがアプリの日付保存規約に従っていない | その値を読む関数の実装を確認してから埋める |
| アバターや添付がプレースホルダのまま | 参照先のパスやリレーションが空 | **UI は変更せず**フィクスチャで埋める |
| 掲載画像が審査で却下される | 価格の記述、または UI が写っていない面 | 5 節を参照 |
| **絵文字が □ で描かれる** | **シミュレータ全体の問題**（実機では出ない）。フォント指定やコードの問題ではない | 同じシミュレータのブラウザで同じ絵文字を出せば 1 回で切り分けられる。**アプリを直そうとしない** |
| **押したはずの選択が反映されていない** | 座標タップが外れても自動化ツールは成功を返す | 文字（`accessibilityLabel`）で押し、要素が出るまで待つ |
| **掲載元が知らないうちに置き換わる** | 巡回用の撮影を掲載元と同じ場所へ書いている | 出力先を分ける |
| **新旧のスロットが混在してストアへ上がる** | スロット名を変えても旧名のファイルが残る | 書き出し前に出力先の画像を消す |
| **タブレットの画像だけ全幅で撮れる／絞られる** | 撮影ハーネスが独自のルートレイアウトを持ち、本体と幅の規則がずれている | 幅の規則を**1 つの関数に集約**して両方から呼ぶ |

### 進め方の教訓

**ソースを読んだ推測より、実行させて値を出すほうが速い。**
表示がおかしいとき、その画面が使っている関数を撮影ハーネスから直接呼んでログに出せば
1 回で確定する。

**「作った」と「効いている」は別。** 生成物を実測して確認する
（画像サイズ、生成された CSS、アップロード後の状態）。

**1 枚のために全体を回さない。** 撮影ハーネスは初回バンドルの待ちが長い。
手順が個別に検証できているなら、直接コマンドを叩いて 1 枚だけ撮り直すほうが速い。

**並べて見る。** 1 枚ずつ確認すると構図の破綻に気づけない。
全スロットを横に並べた 1 枚を作って見ると、間延び・重複・継ぎ目の破綻が一目で出る。

## 8. 本リポジトリでの実体

| 対象 | 場所 / コマンド |
|---|---|
| 実機描画で撮影 → 検証 | `screenshots-mobile`（`scripts/mobile/screenshots.sh`） |
| Storybook から撮影 → 検証 | `screenshots-storybook`（要 `-P store-listing`） |
| 撮影対象の宣言（story id / 端末 / ロケール） | `scripts/mobile/storybook-shots.config.mjs` |
| 検証だけ | `screenshots-validate --platform ios store-listing/ios` |
| **掲載画像の正本** | `store-listing/ios/<locale>/` / `store-listing/android/<locale>/<imageType>/`（gitignore 済み） |
| サイズ → 表示タイプの対応表 | `scripts/mobile/validate-screenshots.mjs` の `APP_STORE_SIZES` |
| App Store へ反映 | `store-push-ios-screenshots [--dry-run]` |
| Play へ反映（文言 + 画像） | `store-push-play-listing [--dry-run]` |
| フィーチャーグラフィック生成 | `build-play-feature-graphic`（要 `-P store-listing`）→ `assets/store/`（**コミットする**） |
| App Store の文言（ASO） | `frontend/apps/mobile/store.config.js` → `mobile-metadata` |
| Play の文言 | `frontend/apps/mobile/play.config.js` |
| ASO の考え方 / 提出チェックリスト | `docs/store/aso.md` / `docs/store/submission-checklist.md` |
| 審査要件のコード側不変条件 | `.claude/rules/store-review.md` |
| リリース手順全体 | `.claude/skills/mobile-release/` |
| 資格情報 | AWS SSM Parameter Store（`config.env` の `MOBILE_SECRETS_SSM_PREFIX`） |

> 撮影ハーネス（`shots/`）は**アプリ固有**なので boilerplate には置いていない。
> 1 節を読んで、そのアプリの画面・フィクスチャに合わせて作ること。
